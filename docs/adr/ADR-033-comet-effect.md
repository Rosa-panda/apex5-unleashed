# ADR-033 灯效「扫描·循环」——原版扫描残留光瑕疵的修复复刻

日期：2026-09-22 · 状态：已实施（同日修订 1、2、3、4）

## 修订 4（2026-09-22，对扫右端常亮诊断闭环 + 用户定稿）

「双色对扫右边永不熄灭」排查全程（真机鉴别表实验，`/api/led/apply_frames` 直写）：

1. **官方驱动争抢（实锤）**：飞智空间站 `SpaceStationService`/`GameViewer*` 在后台
   运行时会把设备改回官方模式（读回 `led_mode=7` 官方彩虹，识别 unknown），
   造成「灯效经常被回退」。用工具箱前应退出官方驱动（服务未禁用，随时可恢复）。
2. **表设计因素（用户定稿）**：对扫 6 帧里两端逐帧同亮——右端品红全循环无熄灭
   时机，孤色观感为「永不熄灭」（左端青色与填充同流不显眼）。用户定稿：
   **铺满后表尾全黑喘息两拍再重开**，两端每轮真正熄灭一次。
3. **相遇融合（用户提出「两边互相扫应相互影响」）**：相遇拍两前端不再硬切边，
   改为 A/B 混色 50/50（奇数灯珠中缝重叠格同样处理）。
4. 帧数 ceil(n/2) → **ceil(n/2)+2**；识别：剥离表尾全黑帧后再验两端同亮，
   中缝允许融合色；测试 4d 同步。
5. 新增诊断端点 `POST /api/led/apply_frames`（bean+frames_b64 直写，绕开生成器）。
6. 实验中观察到「链条末端灭灯可能迟一拍」的疑似设备特性，因官方驱动干扰混杂、
   间歇性出现，未定论；喘息拍同时缓解该观感。鉴别表（单灯三位置+全黑循环）
   可随时重跑复核。

## 修订 3（2026-09-22，用户拍板「全部都做一遍」）

新增六种灯效（生成器 + 识别 + UI 卡片 + 预览步数），全部走 0xA8/0xA9 灯表写入：

| mode | UI 名 | 帧设计 | 帧数 |
|---|---|---|---|
| `rain` | 彗星雨 | 单色光头带 3 珠渐暗拖尾从左掠到右，掠出即全灭重来 | n+3 |
| `chase` | 双色追及 | 固定两色同向环跑，B 三倍速；环上就近归属铺满全带 | n |
| `pulse` | 中心脉冲 | 单色从中心向两端对称扩→收，铺满瞬间回表首 | 2·ceil(n/2)-1 |
| `fire` | 火苗 | 确定性伪噪声（双正弦积）逐帧扰动单色亮度，无随机种子 | 16 |
| `auroraflow` | 呼吸流光 | 三色沿带渐变流动 + 快起慢落呼吸包络 + 行进高光带 | 24 |
| `typewriter` | 打字机 | 逐珠点亮铺满→末珠闪两下→全灭一拍再来 | n+5 |

- 识别顺序插入：clip→全灭→同色系→comet→typewriter→wipe→duosweep→**rain→pulse→
  chase→fire**→rainbow→flow→aurora 兜底。rain 判据 = 每帧连续 run + 左右两半都
  出现过独立 run（光头过境）+ 起点单调 + run 长度 ≤ n//2+1；pulse 全帧 run 含中点
  与之互斥。fire 判据 = 16 帧 + 逐点复算伪噪声亮度容差 0.06 + 通道守卫。
- **修 `led_identify` 残留帧污染**：固件槽位尾部残留旧表帧（擦不掉）会混进判定，
  让自家灯效被认成「外部灯效」。现只看 `loop_start..loop_end` 范围内的帧。
- **对扫「右端常亮」诊断结论**：抓真机灯表（`tools/_led_dump.py`）确认无配置重叠
  （无第二张表、残留帧 loop 之外不播放）。duosweep 帧表两端逐帧同亮是设计使然；
  用户实测左端不亮、且与颜色无关——感知不对称解释被否定，**待固件级排查**
  （怀疑末珠索引在固件播放路径的清位不对称），后续用全灭表/两端 blink 表做
  隔离实验。

## 修订 2（2026-09-22，用户第二批调整）

- 灯效库下架三张卡：心动（heartbeat）、闪烁警报（blink）、警灯流光（flow/period4）。
  **后端生成器与识别保留**（旧灯表进页仍可认出、预览不炸），仅库不再展示。
- 新增「双色对扫」`duosweep`：colors[0] 从左往右、colors[1] 从右往左相向逐珠
  铺满，会合瞬间从头再来。帧数 = ceil(n/2)，中缝相遇处左色优先占位。
  UI 固定两色槽（无加减钮）。识别规则：每帧两端同亮 + 左段 A 色右段 B 色
  （中缝只许全黑、B 段须连续贴右端）——wipe 单端起扫不满足两端同亮，不互混。

## 背景与病灶

用户最喜欢「扫描」（wipe），但观察到：光流到一循环的末尾后，有一盏灯多亮一拍、
灭了之后下一轮才开始（且期望是流完即重新开始，不该有驻留）。

根因在 `protocol.led_frames_wipe` 的帧序拼接，不在固件：

```
fill = [前缀亮帧×n]        # 帧内容：1,2,…,n 班灯亮
return fill + fill[::-1]   # 序列 = 1,2,…,n, n, n-1,…,1  → 循环回 1
```

拼接点把「全亮帧」和「单灯帧」各重复一次：全亮帧多播一拍（光到头滞留）、
循环末尾单灯帧多播一拍（一盏灯赖着不走才开下一轮）。慢速度下（loop_time 大）
肉眼可见的「卡顿+残留光」。

## 修订 1（2026-09-22，用户看真机效果后纠偏）

首版 comet 做成了「带拖尾光头掠过灯带」——用户明确否定：「我要的是光效从左往右，
铺满，铺满以后从头再来，或者可以重来的时候，从右向左」。定稿：

- **帧序 = 逐珠点亮 1..n 共 n 帧，跑满瞬间回表首循环**（用户选了「从头再来」向）。
- 无排空半程、无拖尾、无重复驻留帧；UI 名改「扫描·循环」。
- 识别规则同步改：全前缀帧且亮珠数恰为 1..n 单调递增（须先于 wipe 判定——
  原版扫描亮珠数先增后减，且带倒序半程，二者不混）。

## 首版裁决（已被修订 1 取代，留档）

- **原版 wipe 一字不动**（用户明确要求保留对照）。
- 新增独立灯效 `comet`（UI 名「扫描·掠过」）：带拖尾光头从左扫到右，**完全掠出
  右缘后全灭、立即开下一轮**，全程无驻留帧、无重复帧。
- 帧设计：`tail=4` 级线性拖尾，步数 = rgb_num + tail（末尾 tail 帧为全黑离场帧，
  保证光彻底出界；因表内含全黑帧，不做「长亮」观感）。

## 改动面

- backend `protocol.py`：`led_frames_comet()` + `led_identify` 新增 comet 判定
  （连续 run + 起点单调推进 + 存在全黑离场帧——wipe 无全黑帧，天然区分）。
- backend `engine.py`：`led_apply_effect` 派发表加 comet。
- frontend `Lights.tsx`：Mode/STEPS/ledColor/PadPreview 步数/LIB 卡片。
- 测试：test_led.py 加 comet 生成+识别回环。

## 非目标

- 不改 wipe 生成器、不动原版扫描卡片；
- 不动亮度/帧距标定（MS_PER_LT 沿用）；
- 官方灯表识别逻辑对既有灯效的判定顺序不变（comet 判定插在 wipe 之后、rainbow 之前，
  wipe 无全黑帧不会误判，flow 全帧全亮也不满足「存在全黑帧」）。
