# ADR-019 拓展键映射写通路 + 测试模式（宏前置·任务#8）

日期：2026-09-19（写通路真机验证通过；测试模式当日实现）

## 背景
ADR-016 确认六拓展键（官方名 M1-M6：M1-M4 背部，M5/M6 头部=用户叫法 LM/RM）原生零输出，
0xA3 族映射写入是唯一激活通路。本次打通全链路并交付手柄测试页的六键显示（用户要求全自动完成）。

## 逆向结论（spacestation decomp controller-sdk，NewXInput 分支，校验和帧 5A A5 同 LED 族）
- 完整命令族：161 读槽位状态/版本；162 按 cfgId 应用；163 读配置（cfgId,pkgSize=20 多包）；
  **164 写-开始 [cfgId,startIndex,packetNum,packetSize=20]**；**165 写-数据包 [packNum,20B]**；
  166 保存（永久落 flash，payload=uint16 版本 LE）；173/174 宏独立写通道（与 164/165 同构）；
  175 恢复出厂。
- 配置 blob（真机实测 proto=3.1，42 包×20B=840B）：键表 @13，32 键×3B [目标,turbo,频率]；
  键 id 与官方 device_config_k5.json 一致（18=M1..21=M4, 22=M5, 23=M6）；255=透传，32=宏触发，
  254=键盘映射（用户 M4 官方软件配置过，真实存在）；data_version @225 (u16 LE)=槽位随机 id。
- 官方测试页同用 navigator.getGamepads()，无特权信号源；其 UI 明示「扩展键，实际键值为空」——
  **官方也无法实时显示六键按压**。我们的测试模式（临时映射+双灯）优于官方。

## 真机验证（2026-09-19，全部通过）
- 读：161 活动槽 0、版本表；163 全 blob 读回（注意 hid.read 返回单报告 int 列表，勿再遍历成报告列表）。
- 写：M1→A 弹验证（版本 55677→55678）：42 包写→读回逐字节一致→162 应用→166 保存，
  用户按压实测 M1 灯亮 A（b10.0），映射即刻生效、永久保持。
- 归因映射（版本 55679）写入成功。vendor 流无六键专用 bit（40s 全量抓取零非体感帧）。

## 决定
1. **测试模式**（extkeys.py + service 端点 + PadTest 页）：开=六键映射到 Gamepad API 可见目标
   （M1→select(6) M2→start(9) M3→lb(10) M4→rb(11) LM/M5→thl(14) RM/M6→thr(15)；C/Z 目标弃用——
   标准 Gamepad API 无此二键，显示不到）；关=还原备份 blob。测试页六键灯由 Gamepad API 同位驱动。
2. 键 id↔物理键对应采信官方 device_config_k5.json（位置图权威），不再要求用户受控按压归因。
3. 宏功能（下一任务）在此通路上叠加：键表目标=32 触发宏 + 173/174 宏区独立写入。

## 后果
- 写映射 = 正常用户级配置操作（官方软件同款通道，非固件刷写），风险等级低；仍保留写前自动备份。
- 首个用途：测试页六键实时灯。后续：映射自定义 UI、宏录制/回放、游戏档案挂载键位方案。
- 每次写 blob 全量 42 包 + data_version+1；重复写同槽位安全（erase+rewrite 用户区）。

## 风险
- 162/166 语义按官方 SDK 逆推（应用=激活到输入管线；保存=落 flash），真机行为已验证一致。
- 若用户在官方软件里改键位，两边写同一配置区，后写者胜——测试模式开/关即可重拿控制权。

## 修订 A（2026-09-19 用户拍板：六键要「真·独立新键」，不与老按键重合）
用户指出测试模式六键点亮的是老按键位（视图/菜单/LB/RB/L3/R3），在游戏里会真实触发，重合无意义。
方向改为**虚拟键层**：
- 通道：键表目标=254（映射到键盘）。官方 UI 存在 KeyMapType_Keyboard + mapKeyboardKeyId 体系，
  用户此前的 M4 官方键盘映射即此通道（真实存在、固件原生支持、不经软件）。
- 候选编码：键表 3B 写 [254, 键码, 0]，键码猜 USB HID usage F13-F18=0x68-0x6D（待真机验证；
  备选：键码在第三字节，或固件私有键码表，按压实验一次即知）。
- 验证通过后架构：六键在游戏层零冲突（F13-F18 无游戏响应），键盘接口（MI_01 usage 0x0006）
  输出 F13-F18 → 后端 hidkey 通道解码为虚拟键 MK1-MK6 → 测试页独立 M 灯 / 宏触发 / SendInput
  任意键鼠注入。测试模式（映射老键位）降级为调试工具保留。
- 修正 keymonitor.KEYCODES：0x58-0x63 实为小键盘段（Enter/1-9/0/.），F13-F24 实为 0x68-0x73。

## 修订 B（2026-09-19 终极发现：0xEF 帧含 32 键物理位图——问题彻底解决）
用户要求「深度逆向」后从官方 decomp 找到 `OperatorDataParser` + `NewXInputProtocol`：
- **0xEF 帧（我们一直当体感流）= 官方按键状态唯一数据源**：body[11..14] = keyId 0-31 实时按压位图
  （NewXInputProtocol.ParseData: data[2]==239 → OperatorDataParser.Parse）。
- **位图是映射前的物理按压**：真机验证（用户自由按压，extkey_watch.py）——M3 被映射成 LB 仍报 id20，
  RM 报 id23，真菜单键报 id9，同按 rt+M1 双 bit 并存。**拓展键天然区别于老按键，无需任何映射。**
- 官方 UI 的 `receiveOperatorChanged`/keyStatus 事件即由此来；「扩展键实际键值为空」指的是
  标准键值为空，物理状态它照样有。
- 落地：engine._classify 解码位图（变化才发 `extkey` 事件含 keys[]）→ WS → PadTest 页 M 灯直亮；
  六键固件映射**还原透传 255**（v55684，游戏内零占用）；测试模式映射（修订前方案）废弃为备选。
- 附带逆向：cmd16 读/cmd17 写传输开关（手柄数据/私有原始/键盘/鼠标/第三方控制，255=保持）。
  实测出厂 键盘数据=0（这就是键盘 HID 集合读失败的原因，读错误≠权限问题）；已置 1（键鼠映射备用）。
- 工程附带：桌面快捷方式（pythonw run_gui.pyw 无控制台；pythonw 下 subprocess 必须加
  CREATE_NO_WINDOW，否则 tasklist 每 2s 弹窗）；日志 backend\apex5.log。
