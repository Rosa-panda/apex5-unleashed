# ADR-026：体验区（Experience Lab）——隐藏功能的统一孵化区

日期：2026-09-20 · 状态：**骨架已实现**（注册表 + verdicts + 前端页；功能逐项入驻）
上游文档：《APEX5-功能挖掘-企划书.md》§〇/§三（工作区根目录）· 证据底稿 docs/RESEARCH-HIDDEN-FEATURES.md

## 背景

功能挖掘收官：16 项官方未释放/半释放的功能（体感瞄准、连发 Turbo、曲线编辑器、
设备设置页、仲裁升级、7878 灯效翻译……全清单见企划书 §二）。用户拍板两条产品原则：

1. **全部功能先进「体验区」**——先做进实验专区，真机逐项测试，判定好用才转正进正式导航；
2. 企划书全细节化（已做，防上下文丢失）。

## 决策

### D1：体验区 = 前端独立页 + 后端 /api/exp/* 前缀 + 判定持久化

- 前端：侧栏新导航「体验区」（FlaskConical 图标，设置之前），单页卡片网格
  `pages/ExpLab.tsx`。每卡：名称 / 一句话说明 / 梯队徽标 / 判定三态按钮
  （👍 好用 · ⏸ 待测 · 👎 不好用）/ 状态徽标（孵化中 / 已转正 / 已淘汰）。
- 后端：功能实现模块正常命名（gyro.py / turbo.py / …），API 统一 `/api/exp/<功能>`
  前缀。**转正 = 写转正 ADR + 前端挂载点迁正式导航 + 路由前缀改正式名**，模块零改动。
- 判定：`%APPDATA%\Apex5Unleashed\exp_verdicts.json`，按 feature_id 存
  `{verdict, note, ts}`。转正/淘汰以它为准。

### D2（方案权衡，为什么这样实现更合理）

- **判定存服务端而非前端 localStorage**：判定是「转正决策依据」，要跨窗口、跨前端
  重建、重装不丢，且后端注册表渲染卡片时一并带回（一次请求全知道）。localStorage 在
  pywebview 换壳/清缓存时丢，且前端无权决定「功能存在与否」。→ 服务端 JSON，与
  settings.json / vibfix.json 同款模式（仓库惯例）。
- **注册表驱动 UI 而非前端硬编码卡片**：功能清单在 `explab.py::FEATURES` 一处维护
  （id/名称/说明/梯队/企划书节号/状态），前端只渲染。功能上架=注册表加一行，
  不改前端；判定/状态由后端下发，前端永不过期。单一真相源，防止前后端清单漂移。
- **每功能独立开关、默认全关**：任何功能不得在无用户显式开启时改变手柄行为
  （企划书 §四.4 红线）。体验区互不干扰，一项开着不影响别项。
- **危险项（恢复出厂/DS5）也在体验区**但双确认 + 全量备份先行；它们同样要「测过
  才知道好不好用」。
- 否决的替代方案：每功能一个正式页面（体验期导航爆炸，淘汰项留死页面）；
  不做体验区直接做正式功能（无法回退，用户明确否决）。

### D3：数据流类功能的挂接方式（为 #1 体感/#7 摇杆映射预先裁定）

单 HID 读线程是既有红线。0xEF 帧引擎已在解码（extkeys 位图同源），体感/摇杆映射等
消费端**挂 engine 的帧分发订阅**（同 macro.RECORDER 模式），不另开读线程。

## 后果

- 16 项功能有了统一收容与淘汰机制，正式页面永不被实验性实现污染；
- exp_verdicts.json 成为「哪些功能值得转正」的证据链；
- 代价：转正时有一次路由/导航迁移的小手术（每项一次性成本，可接受）。

## 实现记录（2026-09-20，骨架）

- `backend/app/explab.py`：FEATURES 注册表（16 项，含企划书节号与梯队）+
  Verdicts 读写（%APPDATA%\Apex5Unleashed\exp_verdicts.json）。
- `service.py`：`GET /api/exp`（注册表 + 判定合并）、`POST /api/exp/verdict`。
- 前端 `pages/ExpLab.tsx` + App.tsx 导航「体验区」。
- 功能实现逐项入驻时：在 explab.py FEATURES 对应项置 `enabled: True` 并挂模块；
  详见各功能自己的 ADR。
