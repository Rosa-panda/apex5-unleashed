# ADR-016 拓展键方案：0xA3 映射写入是 6 键可见的唯一通路

日期：2026-09-18（三次修订，最终版）

## 背景
用户要求手柄测试体现拓展键（宏的前置）。八5 共 6 拓展键 =
**LM/RM（头部两键，用户命名）+ M1-M4（背部四键）**。

## 实测事实（逐事件抓取 capture_events.py，用户全程配合按压确认）
1. **6 键全接口零输出**：游戏盘接口 + 键盘接口受控按压逐事件抓取（带时间戳），
   用户明确逐个按过全部 6 键 → 日志零事件。
2. 早期盲抓包看到的 byte10 bit4/bit5 翻转 = 用户按其他键时误碰的杂讯，
   **不是拓展键信号**（用户指认）。据此推翻："FL/FR 直读"方案与 b10.4/5 一切标注。
3. 教训链（用户三次纠偏）：盲抓包无归因 → 受控校准 → 逐事件记录 → 最终确认为杂讯。
   未经归因验证的 bit 标注一律不可信。
4. 空间站通过 cmd 0xA3 读写设备端按键映射配置（服务日志有 0xA3 读 ACK 样本 32B×多包），
   映射写入后按键才有输出。**0xA3 写入是 6 键可见的唯一已知通路。**
5. GitHub 无先例（Apex 4 的 Linux feature request 无人实现）。

## 决定
1. **任务#8（0xA3 逆向）升级为宏功能关键路径**：参照 spacestation decomp
   （ReadMappingConfigCommandNewXInput）+ 服务日志 ACK 样本逆向写格式；
   先写最小映射激活 1 键验证，再铺开 6 键。
2. 激活后键位信号走受控校准归因（keymap.json，逐事件验证），代码不硬编码猜测。
3. 宏功能（v0.2+）建立在 speckey 事件流之上——输入侧统一为一个事件源。

## 后果
- 手柄测试页 6 键位灯全部虚线占位直至 0xA3 激活；校准功能保留（激活后归因用）。
- GamepadRawMonitor 直读保留（描述符外填充位仍需原始读取，激活后普通 API 也可能可见）。
- 发现写入 PROTOCOL.md；capture_events.py 替代 capture_keys.py 作为按键取证工具。
